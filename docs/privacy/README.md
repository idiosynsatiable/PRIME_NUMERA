# Privacy Architecture

Names and birth dates are treated as potentially sensitive personal data.

## Baseline

- Core calculations execute without requiring an account.
- Saving requires explicit user action and consent.
- Public URLs must never encode birth names or birth dates.
- Share records use opaque identifiers and an allow-list of user-approved public fields.
- Analytics events should describe product behavior, not leak calculation inputs.
- Logs and error telemetry must redact profile inputs by default.
- Offline profiles remain local unless the user enables synchronization.
- Deletion/export semantics must be designed before account persistence is considered production-ready.

## Share contract status

The share engine creates 192-bit random IDs, validates bare HTTPS origins for
QR/deep-link targets, and provides store-independent expiration, owner-gated
resolution, and owner deletion operations. The store interface is implemented;
durable persistence, scheduled cleanup, rendering, QR encoding and HTTP
authorization are still required before public launch. An owner ID is private
record metadata and must never be included in public HTML or share images.

## Public share invariant

A person who receives a share URL must not be able to infer hidden birth information from the URL, HTML metadata, analytics payload, QR payload, or server logs generated by the share renderer.
