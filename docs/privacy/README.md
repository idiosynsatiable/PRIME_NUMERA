# Privacy Architecture

Names and birth dates are treated as potentially sensitive personal data.

## Baseline

- Core calculations execute without requiring an account.
- Saving requires explicit user action and consent.
- Public URLs must never encode birth names or birth dates.
- Share records use opaque identifiers and an allow-list of user-approved public fields.
- Analytics events should describe product behavior, not leak calculation inputs.
- Logs and error telemetry must redact profile inputs by default.
- Offline profiles remain local unless the user enables synchronization.
- Deletion/export semantics must be designed before account persistence is considered production-ready.

## Share contract status

The share engine implements 192-bit opaque identifiers, strict runtime payload and
record validation, separate visibility/ownership, expiry, owner deletion and a
public response projection that excludes private metadata. A single-host SQLite
adapter supports insert-only persistence, cleanup and backup/restore; it has not
been provisioned in production. Four SVG card formats and SVG/PNG QR generation
are implemented, including an independent QR decode test.

Authenticated HTTP routes, rate/size limits, CSRF protection, scheduled cleanup,
private deployment storage, encrypted backup/retention policy, deletion replay on
restore, raster card downloads and browser/device verification remain required.
See `packages/share-engine/README.md` for the operational boundary.

An optional public display label is deliberately disclosed text and may identify
the author. Privacy flags describe excluded source fields, not proof that a label
is anonymous or that derived values cannot support inference. Downloads and
copies made by recipients cannot be recalled by deleting the original link.

## Public share invariant

A person who receives a share URL must not receive undisclosed source inputs through the URL, HTML metadata, analytics payload, QR payload, or server logs generated by the share renderer. Only explicitly selected derived values and an approved public label may be disclosed; derived values can themselves reveal limited facts (for example, the selected Birthday value).

## Integrated web application (2026-09-29)

See `../architecture/WEB-INTEGRATION.md` and `../deployment/OPERATIONS.md` for the implemented device-local profile and session-owned share model. The HTTP boundary accepts only a projected payload and enumerated visibility. It rejects labels, raw names/dates, birthday disclosure, extra fields and spoofed ownership. API/share responses are no-store/noindex. A separate revocation journal prevents restored snapshots from resurrecting revoked links. It retains opaque IDs and revocation timestamps indefinitely; the current journal must never be restored backward.

Local profile deletion does not imply revocation of an already-shared anonymous projection. The share manager remains available without an active profile. There is no cloud profile account or sync in this release.
